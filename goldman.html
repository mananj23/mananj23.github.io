Taking LLM calls off the critical path

How I cut the end-to-end latency of a production agentic assistant by 50–60%, with execution accuracy unchanged.

Context

The team runs an internal agentic assistant for advisors in Asset & Wealth Management. An advisor types a request in plain language, and the agent works out what to do and runs the right tools. The agent is built on LangChain and LangGraph and served with FastAPI.

The problem

Before the assistant executed anything, every query passed through three LLM calls, one after another: intent classification, execution planning and tool selection. Each call waits for the one before it, so the delays add up on every request, and the advisor waits through all of them.

The idea

If the assistant can recognise the action an advisor wants while they are still typing, it does not need a model to rediscover the plan each time. The plan for that action can be stored once and run directly.

What I built

1. A typeahead suggestion service

As the advisor types, the service proposes the most likely actions within milliseconds. It combines BM25 keyword detection with prefix and fuzzy search to shortlist candidates, including partial and misspelled input, and then a cross-encoder reranker orders the shortlist so the best action comes first.

2. Templates that encode the whole chain

Each suggestion maps to a MongoDB template that encodes the full tool-and-execution chain. When the advisor picks a suggestion, the template runs directly, and all three LLM calls are skipped.

3. An authoring interface

Templates have to be written and kept current, so I built an interface to author and manage the template library.

4. Integration

The service is integrated into the existing LangChain/LangGraph agent stack on FastAPI. I used gevent monkey patching so that blocking I/O, such as network and database calls, runs concurrently instead of holding up other requests.

Result

End-to-end latency fell by 50–60% at production scale, and execution accuracy stayed the same.

Trade-offs

  • Speed and predictability over flexibility. A lookup is faster and gives the same answer every time, but it only covers actions that have a template.
  • Templates need upkeep. That is why the authoring interface matters as much as the fast path itself.
  • Ranking quality decides the experience. Keyword search alone finds candidates; the cross-encoder makes sure the right one comes first.
